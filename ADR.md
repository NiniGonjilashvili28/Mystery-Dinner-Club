# Architecture Decision Records

## 1. Backend language and framework: Python with Flask

Date: 2026-09-29
Status: Decided
Context: The app needs a small web backend that shows HTML pages and runs as a single process with SQLite. I have to be able to explain every line of it at the comprehension check, and Python is the language I am most comfortable with.
Decision: I chose Python with Flask, using Python's built-in `sqlite3` module to talk to the database.
Alternatives considered: Django, which comes with an admin panel, a user system and its own database layer, but that is much more than two small domains need and would add many files I don't need. FastAPI, which is designed for JSON APIs, but my app mainly shows web pages to people, so its extra features would not help.
Consequences: The project stays small (only 3 packages in `requirements.txt`) and easy to explain, but I have to write some things by hand that Django gives for free, such as SQL queries and a simple login. Flask Blueprints will let me keep the Restaurants and Bookings code in separate parts of the app.

## 2. Keeping the Restaurants and Bookings domains separable

Date: 2026-10-01
Status: Decided
Context: The app must be one process now, but in Assignment 2 it may be split into separate services, so the Restaurants domain (partner restaurants and matching) and the Bookings domain (guests, bookings, reveal, history and ratings) must be easy to pull apart later.
Decision: Each domain has its own folder, its own `schema.sql` with its own tables, and its own Flask Blueprint. Bookings only stores a `restaurant_id` number (no foreign key to the restaurants table) and only talks to the Restaurants domain through the functions in `restaurants/service.py`, such as `find_restaurant_for_booking()` and `get_restaurant_details()`.
Alternatives considered: Letting Bookings query the `restaurants` table directly with a SQL JOIN. It would be shorter, but it would tie the two domains to one shared database, so splitting them later would mean rewriting the Bookings code.
Consequences: `restaurants/service.py` is the seam: if Restaurants becomes its own service, those functions can be replaced by HTTP calls without changing the rest of Bookings. The cost is that the database can no longer check that a booking's `restaurant_id` is real, so the Bookings code has to check it through `get_restaurant_details()`.

## 3. Database design: each domain owns its tables, linked only by an id

Date: 2026-09-30
Status: Superseded by 7
Context: Both domains must store their data in one SQLite file, but they should stay separable (ADR 2). A booking has to remember which restaurant was chosen, so the two domains' data must be connected somehow.
Decision: There are four tables. Restaurants owns `restaurants` and `menu_items`, linked by a real foreign key (`menu_items.restaurant_id` REFERENCES `restaurants`). Bookings owns `users` and `bookings`, linked by a real foreign key (`bookings.user_id` REFERENCES `users`). The only link between the two domains is `bookings.restaurant_id`, which is a plain INTEGER with no foreign key. A rating is stored as two columns on the booking (`rating`, `comment`) because each booking can be rated only once.
Alternatives considered: A foreign key from `bookings.restaurant_id` to `restaurants`, which would let the database guarantee the id is real, but it would force both domains to share one database forever. A separate `ratings` table, which would be needed if a booking could have many ratings, but with one rating per booking it would only add a table and a join.
Consequences: The two groups of tables could be moved into two separate databases without changing the schema. The cost is that the database cannot check that `restaurant_id` is real, so Bookings only saves ids it received from `find_restaurant_for_booking()`. `CHECK` rules (budget at least 30, rating 1 to 5, allowed themes) act as a second safety net behind the Python rules.

## 4. Testing approach: rules first, pages last
Date: 2026-10-01
Status: Superseded by 9
Context: The assignment asks for at least 70% coverage of the core business logic, not of framework glue. My logic depends on the current time (3-day rule, 3-hour reveal) and on random choices (matching), which normally make tests unreliable.
Decision: I put the rules in `restaurants/logic.py` and `bookings/logic.py` as plain functions with no database or web code, and tested them most heavily, including edge cases like exactly 3 days, exactly 30€ and exactly the reveal time. The current time (`now`) and the random generator (`rng`) are passed in as arguments, so tests use a fixed time and a fixed seed. The service and account code is tested against a temporary SQLite database created by the `conn` fixture, and the pages only have a few end-to-end tests with Flask's test client.
Alternatives considered: Testing everything through the web pages. It would look more realistic, but each test would be slower, a failure would not show which rule broke, and time-based rules could not be tested without waiting or changing the system clock.
Consequences: There are 75 tests and 98% coverage of the two domain packages, and the logic files are at 100%. The page tests are deliberately thin, so a visual mistake in a template would not be caught. The one untested line in `restaurants/seed.py` is the "skip if restaurants already exist" path, because every test starts with an empty database.

## 5. Not built: the 3-strikes rule for no-shows
Date: 2026-09-29
Status: Decided
Context: I planned a rule where a guest who does not show up to a reserved dinner gets a strike, and three strikes ban the account, because no-shows cost partner restaurants money. To count no-shows, the app would have to know who did not come, which only the restaurant can say.
Decision: I did not build the 3-strikes rule or any attendance tracking. The app treats every past booking as a dinner the guest attended.
Alternatives considered: Building it with a staff page where restaurants mark each booking as attended or no-show. This needs staff accounts, permissions and a second kind of user, which is close to a third domain and more than the two-domain scope allows in the time I had. Letting guests confirm their own attendance, which is simpler but pointless, because a guest who skipped a dinner would just confirm it anyway.
Consequences: The app stays within two domains and I had time for tests and documentation. The cost is that nothing discourages no-shows, and a guest can rate a dinner they never went to. If it is added later, it would fit as an attendance column on `bookings` plus a strike count on `users`, both inside the Bookings domain.

## 6. Splitting the monolith into a Restaurants service and a Bookings service

Date: 2026-11-15
Status: Decided
Context: Assignment 2 asks me to split the app into two services, each with its own container and its own database. ADR 2 had chosen the seam: Bookings only used the Restaurants domain through three functions in `restaurants/service.py` (`city_overview()`, `find_restaurant_for_booking()` and `get_restaurant_details()`).
Decision: I split along that seam. Each service lives in `services/<name>` with its own Dockerfile, its own SQL Server database and its own database login, and it never reads the other's tables. The three seam functions became three HTTP endpoints on Restaurants: `GET /cities`, `POST /matches` and `GET /restaurants/<id>`. Bookings calls `POST /matches` when a booking is created and `GET /restaurants/<id>` when a revealed booking is shown, through `restaurants_client.py` with a 3-second timeout. The website calls Restaurants directly only to list cities. Because the website is now a separate static site, login uses a signed token sent as `Authorization: Bearer <token>` instead of a session cookie. If Restaurants is down, new bookings are refused with a 503 and a friendly message, while existing bookings, history and ratings keep working and show "restaurant details unavailable".
Alternatives considered: Letting the website ask Restaurants for the match itself and then send the restaurant id to Bookings. That would make Bookings simpler, but the browser would know the restaurant before the reveal, which breaks the main idea of the app, and a user could send any id they want. Putting the shared database code (`db.py`) in one common package used by both services. It would avoid copying the file, but both images would then depend on a folder outside their own, so the services could not be built and changed on their own.
Consequences: ADR 2 mostly held: `logic.py` moved to each service unchanged, and in Bookings only the places that called the seam functions changed (they now receive a `restaurants` client instead of importing the module). What did not survive the split were the HTML pages and the cookie login, which had to be replaced by JSON endpoints and tokens. The costs are a network call with a timeout on every new booking, a new failure mode (Restaurants down) that the code and the website must handle, and `db.py` existing twice, so a fix to it has to be made in both services.

## 7. Data and migrations: one database per service, numbered SQL migrations

Date: 2026-11-20
Status: Decided
Context: In Assignment 1 both domains shared one SQLite file, with four tables in two groups linked only by `bookings.restaurant_id` (ADR 3). Assignment 2 needs one SQL Server database per service, versioned migrations that preserve data, and a plan for a migration that goes wrong in production.
Decision: Restaurants owns `restaurants`, `menu_items` and, since its migration 002, `reservations`. Bookings owns `users` and `bookings`, plus `party_size` since its migration 002. No data was copied over, because the Assignment 1 database only held demo data: the 150 restaurants are seeded again from `seed_data.json` on startup (only if the table is empty), and accounts and bookings started empty. Each service has numbered SQL files in `migrations/` and a small runner of my own (`run_migrations()` in `db.py`): at startup it applies every file not yet listed in `schema_migrations`, in order, and records it in the same transaction, so a migration runs exactly once and a failing one is rolled back. Applied migrations are never edited; a correction is a new file. Integrity lost at the seam: `bookings.restaurant_id` points into another database, so nothing checks that it is real. It is compensated in code: Bookings only saves ids returned by `POST /matches`, the table is reserved by Restaurants itself, restaurants are never deleted (there is no endpoint for it), and if the details ever come back 404 or the service is down, the booking shows "restaurant details unavailable" instead of failing. Recovery plan for a bad migration: (1) if it fails, its transaction is rolled back, the service does not start, the CD health check fails and the run is red, and the database is unchanged; I fix it in a new commit. (2) If it succeeds but is wrong, I write a new migration that corrects it (forward-only, no down-migrations). (3) If it damaged data, I use Azure SQL point-in-time restore (automatic backups for the last 7 days) to restore a copy of the database from before the deploy, and copy the lost rows back.
Alternatives considered: Alembic, a migration tool, which would add SQLAlchemy and Alembic to each service and generate files I would have to learn to read, for two small schemas. Down-migrations, which would let me undo a migration, but they are rarely run and so rarely work when needed; restoring a backup is the safer undo. Copying the Assignment 1 data across, which was not worth it for demo data.
Consequences: Each service can change its tables on its own, and the party size migration showed that existing rows survive (Bookings' 4 bookings on Azure got `party_size` 2). The costs: two copies of the runner (ADR 6), no database guarantee across the seam, and one known gap: if Restaurants reserves a table but Bookings then fails to save the booking, the reservation stays behind and that table is blocked for that time. A cleanup would need a call from Bookings to cancel the reservation.

## 8. Serverless hosting on Azure: pay per use, scale to zero

Date: 2026-11-25
Status: Decided
Context: The system has to run on Azure in my own Azure for Students subscription ($100 credit), only on pay-per-use resources, and stay reachable until grades are published. Nobody uses it most of the day, so paying for anything that runs all the time would waste the credit.
Decision: Everything is in one resource group, `rg-ngonj-exstudents2026`, in Germany West Central (one of the five regions my subscription allows, and one where the free database offer works). The website is a Storage static website (`ngonjexstudents2026ui`, Standard LRS), as the professor's deployment guide asks. Both services run on Azure Container Apps in the Consumption plan (`ngonj-exstudents2026-env`), each with 0.25 vCPU and 0.5 GiB, minimum 0 and maximum 1 replica, and their logs go to the Log Analytics workspace Azure created with the environment. Each service has its own Azure SQL serverless database (General Purpose, Gen5, 0.5 to 1 vCore, locally redundant backups) on one server, `ngonj-exstudents2026-sql`, using the free offer, which pauses the database when it is idle and also when the free amount runs out instead of charging. Images live in GitHub Container Registry, and the pipeline signs in with a managed identity that only has Contributor on this resource group. Cost model: the containers are billed per second while they run, inside a monthly free grant; the databases are free up to 100,000 vCore-seconds and 32 GB each per month; storage costs cents; Log Analytics is free up to 5 GB a month; GHCR is free. In practice my bill has stayed at 0.
Alternatives considered: Azure Static Web Apps for the website, which the first version of the assignment named; the updated guide uses a storage static website, which is simpler to deploy from the pipeline. Keeping one replica always on, which removes cold starts but runs and charges all day. Azure Container Registry, which has a fixed monthly price for something GHCR does for free.
Consequences: Scale to zero has a real cost in waiting time. After a quiet period the first visitor wakes a stopped container (several seconds) that then finds its database paused; resuming takes up to about a minute, and until then connecting fails with error 40613. I saw this myself: one morning the first page took about 40 seconds to show my bookings. The system is built for it: `db.connect()` retries 6 times, waiting 2, 4, 8, 16 and 32 seconds, but stops at once on a wrong password (18456); gunicorn allows 120 seconds; the website waits up to 40 seconds and explains that the servers are waking up when Azure answers 503 itself; and the deploy's health check keeps trying for several minutes. Migrations run at startup, which is only safe because there is at most one replica with one gunicorn worker, so two copies can never run the same migration at once. At 100x traffic I would change: minimum 1 replica so nobody waits for a cold start; more than one replica, which means moving migrations out of startup into a separate step that runs once before the new version takes traffic; more gunicorn workers; the databases off the free offer onto a paid serverless tier with more vCores and no auto-pause; caching `GET /cities`, which rarely changes, and a CDN in front of the website.

## 9. Pipeline and testing: what CI gates on, and a stand-in for the other service

Date: 2026-11-25
Status: Decided
Context: In Assignment 1 every test ran in one process against a temporary SQLite file (ADR 4). Now there are two services, each with its own SQL Server database, an HTTP call with a timeout between them, and a pipeline that deploys every merge to main. The tests have to cover that, and a broken change must never reach Azure.
Decision: CI runs on every push and pull request, once per service. It lints with ruff, starts a throwaway SQL Server with a random password, runs the tests and fails if coverage is under 70% (it is about 95% for both), and builds the Docker image. A third job checks `system.yaml` against the provided schema, checks that both `openapi.yaml` files are valid, and that every endpoint Bookings calls exists in Restaurants' OpenAPI file. CD runs only on main, calls the whole CI first and only continues if it passed on the same commit, then pushes SHA-tagged images, deploys and fails unless both `/health` endpoints answer 200. The tests in each service: pure rule tests with the time and randomness passed in; database tests against the real SQL Server (migrations apply once, seeding twice adds nothing, a wrong password is not retried); API tests through Flask's test client with a fake Restaurants client that can be switched to "down"; client tests with a fake HTTP session that times out or answers 503; and the integration tests across the seam. In those, Bookings runs for real with its database and talks over real HTTP, through its real client and timeout, to a stand-in Restaurants service on a local port that answers like `services/restaurants/openapi.yaml`. One test checks that a booking makes exactly the calls `GET /cities`, `POST /matches` and `POST /reservations` and saves the table number Restaurants chose; the other makes the stand-in slow and checks that Bookings answers 503 within the timeout while the booking list still works. I used a stand-in instead of the full compose stack because each service's CI job runs on its own, starting SQL Server and both services for every run would be slower, and with a stand-in I can make Restaurants slow or broken on purpose, which is the case that matters most.
Alternatives considered: Running the integration test against the whole compose stack, which tests the real Restaurants service but cannot easily make it slow, and needs both images built before any test runs. A contract-testing tool such as Pact, which keeps a stand-in honest automatically but is another tool to learn and run. Browser tests of the website with Playwright, which are slow and break easily when the page changes.
Consequences: Nothing reaches Azure without passing lint, tests, coverage, the image build and the system.yaml check. The risk of a stand-in is that it drifts from the real service; this is limited because the stand-in follows the OpenAPI file and CI checks that every endpoint Bookings calls is in that file, and the real services talk to each other in compose and after every deploy. Deliberately not tested automatically: the website's JavaScript (I check it by hand in Chrome and Safari), the Azure commands in `cd.yml` (they only run during a deploy, and the health check catches a broken one), migrations on the real Azure database (CI never touches Azure SQL), how long a cold start takes, and two guests reserving the same table at the same moment (the UNIQUE rule in the database is the safety net).
